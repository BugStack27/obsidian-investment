# 交易记录日期格式防护 — 决策记录

> 状态：✅ 已验收（2026-10-22）

## 1. 目标与范围
把「什么算合法的记录日期」收敛为单一共享口径，让弹窗录入、批量导入、解析读取三条路径共用：弹窗日期改为原生日期控件并在保存时兜底校验，解析口径适度放宽使笔记里已写坏的 `2026-7-8` 重新可见。不做：渲染时回写笔记、新增手动修复命令。

## 2. 关键决策
| 决策点 | 结论 | 理由 |
|------|------|------|
| 录入控件 | 原生 `input[type=date]` | value 恒为 `YYYY-MM-DD` 或空串，格式错误从源头不可能产生；零新增依赖 |
| 日期可选范围 | 不限制（不加 `max`） | 用户会预录已挂单的成交；交易日限制会误拦基金确认日 |
| 存量坏行处理 | 放宽解析口径并自动补零 | 只防新增会让存量坏行继续静默丢失 |
| 合法判定归属 | 抽共享工具函数，三处共用 | 避免解析与导入口径再次分叉 |
| 放宽范围 | 仅「年-月-日」，月/日允许 1-2 位；拒绝日历上不存在的日期 | `/`、`.` 分隔符扩大传入面；`20260708` 紧凑写法误识别风险高 |
| 是否回写文件 | 只读归一化，不改笔记原文 | 「打开笔记即写盘」会污染同步与版本控制；用户下次编辑保存时自然规范化 |

## 3. 交付物
| 文件（相对路径） | 职责 |
|------|------|
| `src/utils/recordDate.ts` | `isValidRecordDate`、`normalizeRecordDate`、`todayStr` |
| `src/utils/recordParser.ts` | `parseRecordLine` 改用 `normalizeRecordDate`，返回归一化日期 |
| `src/utils/importExport.ts` | 导入侧改用同一归一化口径，不合法仍计入 `invalidRows` |
| `src/ui/positionTradeModal.ts` | 日期行改为原生日期控件；构造阶段归一化 `init.date`；`save()` 补格式兜底 |
| `styles.css` | `.inv-date-input` 宽度对齐 |

## 4. 关键修正与教训
- **编辑旧记录时日期控件显示为空白** → 控件只接受合法 ISO 或空串，`init.date` 必须先经 `normalizeRecordDate` 归一化（失败退回今天），否则保存即抹掉原日期。
- **先设值再改 `type` 会被浏览器重新 sanitize 清空** → 必须先赋 `type = 'date'` 再 `setValue`。
- **控件允许被清空** → 不能只靠控件兜底，`save()` 必须保留 `isValidRecordDate` 校验。
- **`placeholder` 对日期控件无效** → 删除无效的 `YYYY-MM-DD` 占位符代码。
- **`isValidRecordDate` 若实现为「归一化不为 null」会放行 `2026-7-8`** → 必须实现为「归一化结果等于原串」，两函数语义才不重合。
- **`new Date` 会把 0-99 年份映射到 19xx** → 归一化时须显式限制年份范围并用回读比对拦下 `2026-2-30`。

## 5. 已知边界
- 编辑场景若 `init.date` 不可归一化（如 `2026/7/8`），控件会显示今天、直接保存即静默改写；该路径不可达——此类行已被解析丢弃，进不了表格。
- 原生日期控件在部分平台仍允许键盘分段微调，但产出值恒为合法 ISO 或空串。
- 未纳入本次：解析失败行不计数不告警（另见 [unparsed-trade-lines.md](unparsed-trade-lines.md)）、多记录块只取首块、类型非法的行仍静默丢弃。
