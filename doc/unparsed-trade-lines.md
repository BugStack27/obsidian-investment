# 标出无法解析的交易行及行号 — 决策记录

> 状态：✅ 已验收（2026-10-24）

## 1. 目标与范围
记录块解析时原本对不合法行一律静默丢弃，用户无从感知漏记。本次在解析产物中附带「无法解析的疑似交易行」清单（块内行号 + 失败原因），并在基金 `record` 块与股票 `stock-record` 块顶部各给一行只读提示。关键约束：不改变任何「哪行算合法」的判定，`entries` 产出必须与改动前逐行一致。

## 2. 关键决策
| 决策点 | 结论 | 理由 |
|------|------|------|
| 行号口径 | 块内相对行号（1 基，fence 行不计） | 与 `entries.lineIdx` 同基准，用户数源码块内行即可对上 |
| 哪些行算「无法解析」 | 仅疑似记录行：首列为类型词，或列数 ≥ 3 且有一列像日期 | 避免把块内说明文字、标题误报成坏行 |
| 提示详细程度 | 列行号 + 失败原因，超过 10 条折叠为「等 N 行」 | 只列行号用户仍需自己比对；全列会撑高块顶部 |
| 是否支持点击跳转 | 不做，纯文字提示 | 记录块与源码同屏，编辑器定位 API 验证成本不划算 |
| 文案归属 | 基金块与股票块共用同一渲染函数 | 两份文案迟早漂移 |

## 3. 交付物
| 文件（相对路径） | 职责 |
|------|------|
| `src/types.ts` | `RecordLineError`、`UnparsedRecordLine`；`RecordParse` 新增 `unparsed` 字段 |

## 4. 关键修正与教训
- **`parseRecordLine` 返回 null 有两种含义** → 空行/注释与解析失败必须区分，否则所有空行会被报成坏行；只有后者进 `unparsed`。
- **行号基准必须保持块内 0 基** → 与 `entries.lineIdx` 一致，只在渲染文案时 `+1`；解析层提前 `+1` 会导致后续编辑/删除错位。
- **类型白名单曾出现两份真相** → 统一走 `isKnownType`，否则新增类型只改一处会把合法新类型判成 `type` 失败。
- **提示不能放在表格的空状态分支里** → 该分支提前返回，全部行都是坏行时提示会丢失。
- **`buy,2026-05-17`（两列、金额缺）本就解析成功**（金额按 0） → 不得出现在 `unparsed` 中；单列 `buy` 才是「列数不足」的真实触发例。
- **`unparsed` 为空时不得创建任何 DOM** → 否则合法笔记的块高度也会变化。

## 5. 已知边界
- 启发式判定有误报：`备注,2026-05-01,说明` 这类「三列且含日期样串」的说明行会被报为「类型无法识别」，只增噪音不影响计算。
- 覆盖缺口：`bught,2026-05-15`（类型拼错且列数 < 3）仍静默；`买 入` 这类首列含空格的写法不报。
- 本功能只观测不改判定，金额为 0、份额为 0 等仍按现状放行；多 `fund-record` 块只取首块仍是既有边界。
- 数据中枢、近期交易、总览卡片不提示坏行。

## 6. 后续候选
- 点击行号跳转源码并定位光标（本次已否决）。
- 收紧「疑似」判定以减少误报，代价是可能漏掉中文类型词等高频真实错误。
